Code + collaboration

GitHub

Google Docs for code: a free place to store projects, track every change, and work on them with other people. It can also turn a project into a live website.

By GitHub (owned by Microsoft)

Jump to the full step-by-step walkthrough ↓

Quick demo

What it is

GitHub is a website built on Git, a tool that saves every version of your files. A project lives in a repository (repo), which is just a folder with a full history. You can see who changed what and go back to any earlier version. This club site is a GitHub repo, and its website is hosted by GitHub too.

Why people use it

  • Nearly every software team and AI project, including most open models, keeps its work on GitHub.
  • Teams review each other's work before it goes live, which prevents costly mistakes.
  • GitHub Pages hosts a website from a repo for free, with no server to manage.
  • A public GitHub profile works as a portfolio that employers and investors can check.

How to get started

  1. Create a free account at github.com.
  2. Open this club's repo (TheJ1u/ai-for-life) and click around. Every file is readable.
  3. Click Fork to make your own copy. You cannot break the original.
  4. Open a file, click the pencil icon, make a change, and Commit it. A commit is a saved version with a note.
  5. Click Contribute, then Open pull request to suggest your change to the club repo. The owner reviews it and clicks Merge if it looks good.

Try this

git clone https://github.com/TheJ1u/ai-for-life.git
cd ai-for-life
git add .
git commit -m "Describe what you changed"
git push

These are the commands for working on your own computer. To start, skip them: you can do everything above in the browser. Learn the commands once you have made a few changes on the website.

Why it matters for business and IS

Information Systems angle: GitHub is how organizations control change. Every edit is recorded, reviewed and reversible, which supports audits, teamwork and quality. For a startup it also means a website or product can launch with almost no hosting cost.

Full walkthrough: from zero to your first merged change

Read this top to bottom once, then keep it open while you do the steps. Every step can be done in your web browser. You do not need to install anything or know how to code.

1. The idea in business terms

Imagine a shared Google Doc where every edit is saved with a name, a date and a note, nothing is ever lost, and a manager must approve changes before they go public. That is GitHub. The words are different, but the ideas match:

  • Repository (repo): the project folder. Ours is TheJ1u/ai-for-life.
  • Commit: one saved version, with a short note about what changed.
  • Branch: a side copy where you try changes without touching the main version.
  • Fork: your own copy of someone else's repo, in your account.
  • Pull request (PR): a request that says "please add my changes to the main version." This is the approval step.
  • Merge: the owner accepts the request and the change goes live.

Information Systems link: this is called change management. Companies need to know who changed what, why, and whether someone approved it. GitHub builds that into the tool.

2. Set up your account (10 minutes)

  1. Go to github.com and choose Sign up. Use an email you check.
  2. Pick your username carefully. It appears in every link and on your resume, like github.com/yourname. Use something professional, such as your name. Changing it later is possible but breaks old links.
  3. Verify your email when GitHub sends the message.
  4. Turn on two-factor authentication in your account settings (look for Password and authentication). This protects your account and your public profile if someone steals your password.
  5. Optional but smart: add a profile photo and a one-line bio. Employers do look.

3. Take a tour of a repo page

Open github.com/TheJ1u/ai-for-life and look at these parts:

  • File list: every file and folder. Click any file to read it.
  • README: the welcome text shown under the file list. Good projects explain themselves here.
  • Commits (a clock icon with a number): the full history. Click one to see exactly what changed, with red for removed and green for added.
  • Issues tab: a to-do and idea list. Anyone can open an issue to suggest something.
  • Pull requests tab: proposed changes waiting for review, and the history of accepted ones.
  • Settings tab: only the owner sees it. That is where the website (GitHub Pages) is turned on.

4. Make your first change without breaking anything

You cannot damage the club repo. You are not editing it; you are proposing a change to it.

  1. Sign in. Open the repo and click a file you want to improve, for example glossary.html or CONTRIBUTING.md.
  2. Click the pencil icon (Edit this file). Because you are not the owner, GitHub will offer to fork the repo for you. Accept. It makes your own copy automatically.
  3. Make a small change. Fix a typo, add one sentence, or add your name to the Contributors table.
  4. Click Commit changes (or Propose changes). Write a short message that says what you did, like Add Muse tool guide. Good messages start with a verb and are under about 70 characters.
  5. GitHub then shows Create pull request. Click it. In the box, explain in one or two sentences what you changed and why. Click Create pull request again.
  6. Done. You will get an email when the owner comments or merges. Your change goes live on the website a minute or two after it is merged.

If the owner asks for a fix, edit the same file on your fork again and commit. The pull request updates itself. You do not need to start over.

5. What to write in a pull request

A clear request gets merged faster. Use this pattern:

What I changed: Added a guide for Muse and linked it on the home page.
Why: We talked about it at the Thursday meeting and it was not on the site.
How I checked it: Opened the page, clicked every link, ran scripts/update_site.py.

6. Undo a mistake

This is the part that makes GitHub safe. Nothing is ever really lost.

  • Before it is merged: just close the pull request, or keep editing it.
  • After it is merged: open the merged pull request and click Revert. GitHub makes a new pull request that undoes it. The owner merges that, and the site goes back.
  • To see an old version: open a file, click History, and click any earlier version.

7. Use branches (when you are ready)

A branch is a safe lane for one piece of work. If you have write access to a repo, open the branch dropdown (it says main), type a new name like add-muse-guide, and choose Create branch. Your commits go to that branch only. When it is ready, open a pull request from the branch into main. Teams use one branch per task so unfinished work never reaches the live site.

8. Start your own repo and publish a free website

  1. Click the + at the top right, then New repository. Name it something short with no spaces, like my-portfolio. Choose Public and tick Add a README.
  2. Click Add file, then Create new file. Name it index.html. Paste a few lines of HTML (ask Claude: "write a simple one-page personal site in a single HTML file"). Commit.
  3. Go to Settings, then Pages. Under Build and deployment, choose Deploy from a branch, pick main and / (root), and click Save.
  4. Wait one to two minutes and refresh. GitHub shows the address: https://YOUR-USERNAME.github.io/my-portfolio/.
  5. Every future commit updates the site automatically.

9. Issues: the club's idea box

Not ready to change a file? Open the Issues tab, click New issue, write a title and a few sentences ("Add a guide for Google AI Studio"), and submit. Anyone can then pick it up. In a company, issues are the task list.

10. Working on your own computer (do this second, not first)

The browser is enough to start. When you make many changes, the desktop way is faster.

  • Easiest: install GitHub Desktop (free, from desktop.github.com). Sign in, choose Clone a repository, edit files in any editor, then use Commit and Push origin buttons.
  • Commands: the same thing with text commands in a terminal:
git clone https://github.com/YOUR-USERNAME/ai-for-life.git   # download your fork
cd ai-for-life
git pull                                  # get the newest version first
git status                                # what did I change?
git add .                                 # choose all my changes
git commit -m "Add Muse tool guide"       # save a version with a note
git push                                  # send it to GitHub

Always git pull before you start. It prevents most conflicts.

11. Use AI to help, safely

This repo has a CLAUDE.md file with instructions for AI assistants. If you open the repo in Claude Code or paste the repo link and the file into Claude, it follows the club's rules (format, no invented facts, run the update script). You are still responsible for what you submit, so read the change before you commit it.

12. Keep secrets out

  • Never commit passwords, API keys, tokens, client names, or Medicare details. A public repo can be read by anyone and by bots that scan for keys.
  • If you commit a secret by mistake, deleting it is not enough because it stays in the history. Revoke or change the key right away, then tell the owner.
  • Use a .gitignore file to list files that should never be uploaded, such as .env.

13. When something goes wrong

  • "This branch is out of date": the main repo changed while you worked. On your fork's page click Sync fork, then try again.
  • Merge conflict: two people edited the same line. GitHub shows both versions. Keep the correct text, delete the markers (lines with <<<<, ====, >>>>), and commit. Ask in the club chat if unsure.
  • My change is not on the website: wait two minutes, then hard refresh (or open in a private window). The browser may be showing an old copy.
  • No pencil icon: you are probably not signed in.
  • Push rejected: run git pull first, then push again.

14. Your practice ladder

  1. Create your account and turn on two-factor authentication.
  2. Add your name to the Contributors table through a pull request.
  3. Add one new term to the glossary.
  4. Open an issue with an idea for the site.
  5. Create your own repo and publish a one-page site with GitHub Pages.
  6. Install GitHub Desktop and make a change from your computer.

15. Why this helps your resume

Each merged pull request is public, dated proof that you contributed to a real project. Link to your pull requests from your resume and from the Contributors page. Pin your best repo on your GitHub profile so it is the first thing a recruiter sees.

Business use case

Scenario: A student team or startup needs a simple landing page and wants everyone to be able to edit it without breaking the live site.

How it works: Put the site in a repo, publish it with GitHub Pages, and have teammates propose edits as pull requests. The owner reviews each one before it goes live.

Measure success by: Hosting cost (zero), time to publish a change, and fewer mistakes reaching the live site.

Watch out for: Never commit passwords, API keys or private customer data. A public repo is readable by anyone.
